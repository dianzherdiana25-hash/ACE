## 1. The change under test (specified now, built only on activation)

**Lineage labels.** Every code text in a solve carries a
lineage label, assigned when the text first enters the
solver's `seen` set (first-generation-wins, mirroring the
stock `seen` dedup and provenance rules):

- the task's start code is **BASE**;
- a variant generated from a BASE parent by a baseline
  step (the adapter's `baseline_variants`) stays **BASE**;
- any variant generated by an extra-key or extra-chain
  step, and every variant generated from an
  ENRICHED parent regardless of step, is **ENRICHED**.

BASE is therefore exactly the set of codes reachable
without the admitted catalog — the catalog-only lineage
whose round-1 frontier death is the measured mechanism
(PR #184 §1: on both development witnesses the frontier
after round 1 holds a single, enriched-provenance member,
and the winning code is never generated afterwards).

**The guard (one form, registered in advance).** Frontier
construction is stock — top-W by shown score, stable
enumeration tie-break, filter score >= best — with ONE
modification: if the resulting frontier contains no
BASE-lineage member AND at least one BASE-lineage
candidate was scored this round, the frontier's
lowest-ranked member is replaced by the round's
highest-scoring BASE-lineage scored candidate (ties by
stock enumeration order). Frontier width, enumeration,
scoring, cap behaviour, shown-perfect early exit and
termination are otherwise unchanged.

Forms considered and rejected in advance, with reasons:
appending a (W+1)-th slot instead of replacing (changes
frontier width — the variable PR #184's `frontier_only`
cell already showed non-binding; a width change would
confound the guard with a dead variable); two-phase
catalog-only-first solving (PR #173 §5's M1-form — a
larger change that discards the enriched search's
measured benefits instead of protecting the lineage
inside it; it remains the named fallback if this guard
is refuted while the lineage account is confirmed again).

## 2. The lineage anchor — what must be proven per round

The guard is measured by a dedicated instrument, the
**lineage anchor**: an instrumented run layer (harness-side,
over the same gated solver family as PR #184) that emits,
per task, a per-round lineage record and checks the
invariants below. Record schema name (reserved here):
`ace.lineage_anchor.v1`. Per round r, the record carries
frontier_in and frontier_out composition by lineage
(member sha256 + label), the scored BASE candidates'
best score and rank, the reserved slot's occupancy
(occupant hash + displaced hash, or "not triggered"),
and the true-path candidate's per-round fate (the
PR #184 §7.3 fields). What the anchor PROVES:

- **L1 — Membership.** For every round, exactly which
  lineage holds frontier membership — counts and hashes,
  in and out. (The development witnesses' stock record:
  BASE membership is zero from round 2 onward; the anchor
  must reproduce that record on those witnesses before
  it is trusted anywhere else.)
- **L2 — Continuity.** Per task, the lineage-survival
  bit per round (BASE alive in frontier_in: yes/no) and
  the **lineage death round** — the first round whose
  frontier_in holds no BASE member. This is the quantity
  the guard exists to move: under stock it is round 2
  (death at the round-1 selection) on both witnesses.
- **L3 — True-path fate in lineage terms.** For tasks
  the clean condition solves and the infected condition
  fails, the clean winning code's classification
  (PR #184 taxonomy) reported alongside the death round,
  so "the winner was never generated" and "its lineage
  died at round r" are one joined fact, not two anecdotes.
- **L4 — Non-perturbation.** The lineage instrumentation
  itself passes the §7.2 logging-invariance gate
  (stock vs instrumented: identical returned hash,
  solved, score calls, provenance trace) on the
  development witnesses before any guarded run is read.
  A gate failure voids the instrument, not the guard.
- **L5 — Actuation.** In every guarded run, wherever the
  guard's trigger held, the reserved slot's occupant IS
  the round's argmax BASE scored candidate. A single
  violation voids the run as instrument failure — this
  separates "the guard does not work" from "the guard
  was never actually applied", which must never be
  confounded in the verdict.

## 3. The inoculation battery as the guard's gate (PR #175)

Before the guarded solver measures anything on any
evaluation band, it must pass the standing battery —
the battery is the gate, not a reporting accessory:

- **Gate run.** `regression_anchor.py --inoculate`
  (PR #175 wiring) with the battery's `solve` bound to
  the GUARDED solver, over every distractor in the
  registry as it stands at activation (today: the seed
  `name-swap-523014-nc-band20261501`, witnesses
  catalog_control-020/-021; the gate automatically
  extends to any further registered distractors —
  Stage 3's fresh bands may add entries by the
  registry's existing evidence rule; this framework
  creates none).
- **Pass condition.** Overall battery verdict
  NOT_SUSCEPTIBLE under the guarded solver: every
  registered witness solved clean AND injected. This is
  the guard's purpose stated in the battery's own
  grammar — the demonstrated SUSCEPTIBLE of PR #175
  (stock solver) is what must flip.
- **Positive control.** In the same session, the same
  battery bound to the STOCK solver must still read
  SUSCEPTIBLE. A session where stock reads
  NOT_SUSCEPTIBLE is void (witness/catalog state is
  wrong), whatever the guarded side shows.
- **No-collateral condition.** The anchor's main verdict
  for guarded vs stock on its standard battery must be
  NO_REGRESSION, and a SUSCEPTIBLE result blocks
  adoption under the anchor's standing consequence rule
  — both inherited unchanged from PR #167/#175.
- The gate runs on the witnesses (development data, used
  as an instrument check). It is necessary, never
  sufficient: adoption additionally requires §4.

## 4. Confirmation measurement (specified now, seeded at activation)

- **Band.** A fresh seed band named in the activation
  act, disjoint from 20261501–20261503, from the Stage 3

  Universe/catalog/control construction identical to

  and the clean × infected conditions (registered
  distractors injected at the end, PR #175 form).
- **Arms.** Stock vs guarded — the guard is the ONLY
  difference (same harness, same logging, same
  uncapped form). The lineage anchor (§2) records both.
- **Endpoints, read paired (§8(a)) with cost visible:**
  primary — recovery of the witness class: tasks solved
  by stock-clean, failed by stock-infected, solved by
  guarded-infected (recovery = PR #184 §2.5: solved on
  holdout, never hash equality); no-harm — tasks solved
  by stock-clean must remain solved by guarded-clean,
  per task; cost — median score-call ratio guarded/stock
  per task class, with the 3× recovery-at-cost reporting
  threshold inherited from PR #184 §2.5; lineage —
  survival curves and death-round distributions from
  the anchor, per arm.
- **Empty-phenomenon rule.** If the band's infected
  condition diverts no task under stock, the item closes
  NOT_REPRODUCED on that band (the gate result of §3
  still stands as an instrument record). No band fishing.

## 5. Verdict criteria

- **GUARD_ADOPTED** — iff ALL hold: (a) §3 gate passes
  (NOT_SUSCEPTIBLE on every registered distractor,
  positive control SUSCEPTIBLE under stock, anchor
  NO_REGRESSION); (b) §4 recovers EVERY witness-class
  task on the confirmation band (with small n, all —
  the same restoration standard leave-one-out set in
  Stage 1); (c) zero clean-condition harm; (d) median
  cost ratio on recovered tasks <= 3×.
- **GUARD_PARTIAL** — gate passes and §4 recovers at
  least one but not all witness-class tasks, with zero
  clean harm. Not adopted; the record stands, mechanism
  refinement returns to design, and the same band is
  never re-run for a better number.
- **RECOVERY_AT_COST** — (a)–(c) hold but the cost ratio
  exceeds 3×. The numbers are reported with the cost in
  the verdict's own sentence; adoption is escalated to
  hub ratification, never automatic.
- **GUARD_REFUTED** — any of: gate fails (battery still
  SUSCEPTIBLE under the guarded solver); §4 recovers
  none of the witness-class tasks; or clean-condition
  harm >= 1 task (harm with recovery is recorded as
  GUARD_HARMFUL and equally blocks adoption).
- **VOID** — L4 invariance failure, L5 actuation
  failure, positive-control failure, or an absent
  activation condition. A void run is an instrument
  record, not evidence about the guard.
